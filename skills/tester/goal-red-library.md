Stage RED, for a library or a command-line tool. Write tests that fail now and pass once the change exists, against what its users depend on: the public API (what other code imports and calls) and the command line (commands, flags, output and exit codes). Test the public API through its documented entry points, not internals. For command-line behaviour, add golden cases in `tests/golden/`: `<name>.cmd` holds the command, run from the repository root with `sh` (e.g. `PYTHONPATH=src python3 -m tool --flag x`), `<name>.out` its exact expected stdout, and `<name>.code` the exit code when it isn't 0; cover errors and usage messages too. The factory runs them after the implementation and compares byte for byte, so keep output deterministic: no dates, paths or timing. When a command reads stdin or emits non-ASCII text, test it by running the real entry point in a subprocess under a non-UTF-8 locale (e.g. `LC_ALL=C PYTHONUTF8=0`) rather than monkeypatching `sys.stdin` or similar, so encoding failures in the real process show up. Existing public behaviour must keep working unless the request changes it: add tests that pin it where the change could break it. Make sure a `.gitignore` covering generated files such as `__pycache__` and `.pytest_cache` exists before the first commit, so no build or test artifacts get committed. Run the tests and make sure they fail for the right reason.
